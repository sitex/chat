# Спецификация: WARNING при `auto → ollama`

## Цель

Сделать неявное переключение LLM-резолюции в `ollama` наблюдаемым для оператора, не добавляя предупреждений на штатные пути выбора бэкенда.

## Граница уровней логирования

### `WARNING`

`WARNING` записывается только в `_resolve_backend()` при одновременном выполнении условий:

1. `LLM_BACKEND` имеет значение `auto` (включая значение по умолчанию).
2. Недоступны все upstream-кандидаты auto-каскада: `cliproxy`, `grok`, `claude-cli`, `claude`.
3. Резолюция поэтому возвращает финальный fallback `ollama`.

Текст одного предупреждения обязан объяснять **причину**, а не только сообщать выбранный результат:

- явно указывать, что ни один из `cliproxy`, `grok`, `claude-cli`, `claude` недоступен;
- для `cliproxy` называть отсутствующие `CLIPROXY_API_KEY` и/или `CLIPROXY_BASE_URL`;
- для `grok` и `claude-cli` называть ненайденные пути бинарников;
- для `claude` называть отсутствие `ANTHROPIC_API_KEY`;
- сообщать, что вследствие этого выбран `ollama`.

### Без предупреждения

- Явный `LLM_BACKEND=ollama` — осознанная операторская конфигурация, логируется только существующей штатной телеметрией `INFO` из `generate()`.
- Успешная auto-резолюция в `cliproxy`, `grok`, `claude-cli` или `claude` — штатный путь, `WARNING` не создаёт.
- Явный выбор любого поддерживаемого бэкенда — не добавляет предупреждения на этапе резолюции.

## Неизменяемое поведение соседних путей

Runtime-каскад в `_cascade()` не меняется:

- отказ выбранного бэкенда с переходом на следующий уже является `WARNING`;
- `claude-cli` в strict-режиме остаётся `ERROR` с повторным возбуждением исключения;
- общий timeout в `generate()` остаётся `ERROR`;
- успешный вызов продолжает писать один `INFO` с backend/model/latency;
- fallback `summarize()` от выделенного Claude CLI в основной каскад остаётся `WARNING`.

Проверка доступности чат-модели или HTTP-сервера Ollama не добавляется: событие для этого изменения — именно достижение финального fallback при `auto`.

## Компоненты

- `chatcore/llm.py`
  - `_resolve_backend()` определяет единственную новую точку `WARNING`.
  - Вспомогательная функция формирует диагностическое описание недоступности всех upstream-кандидатов.
- `tests/test_llm.py`
  - один тест фиксирует `WARNING` для `auto → ollama` и полный набор диагностических причин;
  - второй тест фиксирует отсутствие `WARNING` при явном `LLM_BACKEND=ollama`.
- `CHANGELOG.md`
  - содержит запись о том, что неявный fallback `auto → ollama` стал наблюдаемым и как намеренно выбрать тихий Ollama-режим.

## Критерии приёмки

1. При `LLM_BACKEND=auto` и недоступности всех upstream `_resolve_backend()` возвращает `ollama` и пишет ровно одно диагностическое `WARNING`.
2. Сообщение `WARNING` содержит имена четырёх upstream-кандидатов и причины их недоступности.
3. При `LLM_BACKEND=ollama` `_resolve_backend()` возвращает `ollama` без `WARNING`.
4. При успешной auto-резолюции в один из upstream предупреждение не появляется.
5. Существующие уровни логирования runtime-каскада, strict-режима, timeout и `summarize()` не меняются.
6. Целевые unit-тесты проходят вместе с полным набором `tests/test_llm.py`.

## Вне области работ

- fail-fast в конкретных ботах и их `envcheck.py`;
- новые переменные окружения или изменение порядка auto-каскада;
- проверка доступности сервера Ollama, загрузки чат-модели или качества ответа;
- изменение fallback-маршрутов `_cascade()`.
